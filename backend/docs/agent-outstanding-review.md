Newly prepared objectives have one primary lesson and two rubric-backed Basic starter questions. The Tutor can request the other formats at the selected difficulty. ### Question progression and grading

Use the progression below when choosing starter and requested questions. The Expert assigns each question a learning objective, difficulty, and format. The Tutor can request a harder format when the learner shows readiness, or a simpler one to isolate the cause of a mistake. The verifier checks the reasoning required as well as the response format.

| Default progression | Ability being tested | How the answer is graded |
| --- | --- | --- |
| Basic · Single-answer multiple choice | Recognize a fact, concept, or rule. | Compare the selected option with the private key. |
| Intermediate · Multiple-answer multiple choice | Distinguish several valid conditions, examples, or claims. | Require at least two correct options and one distractor. Compare the selected set with the exact key. Award partial credit only where a criterion defines it. Selecting every option earns no credit. |
| Intermediate · Fill in the blank | Recall a term, complete a step, or produce a short result without options. | Check each named blank against authored equivalents, with optional case sensitivity. Numeric questions specify units and rounding in the prompt and include accepted forms in the key. Possible equivalents outside the key are uncertain and receive no automatic full credit. |
| Advanced · Open question | Explain reasoning, justify a choice, or apply several ideas. | Score a source-backed rubric by criterion, citing evidence from the learner's answer. Accept valid alternative reasoning that meets the rubric. Record uncertainty where the answer or sources are ambiguous. |

Record and verify the objective's evidence requirements before assigning practice. Starter questions provide Basic practice. If the target requires application or justification, request an appropriate question when the learner is ready. Demonstration requires two distinct, unassisted, rubric-meeting responses at the target difficulty. Partial, hinted, and uncertain responses remain diagnostic evidence. [Current evidence rules](../learnloop/core/domain.py)

### Proposed automatic verification gate

The Expert owns drafting, reviewing, and repairing materials. Its reviewer runs in a fresh model call with a fixed checklist and the relevant course passages. A separate runtime check controls publication. Here, **verified** means the exact artifact passed the configured checks against the available sources.

| Step | Check and outcome |
| --- | --- |
| 1. Validate structure | The runtime checks schemas, course-scoped passage IDs, valid graph references, acyclic prerequisites, required coverage, question counts, unique prompts, and rubric structure. A failure returns a specific issue for the Expert to repair. |
| 2. Review meaning | The Expert reviewer checks source support, prerequisite direction, lesson scope, and question difficulty. Ask the reviewer to solve each question from the passages before showing the key or reference answer. Check option sets for ambiguity, blank answer variants and units, and whether the open-question rubric accepts valid alternative reasoning. Return `pass`, `repair`, or `insufficient_evidence` with item IDs, evidence references, and reasons. Use a second verifier, preferably a different model, for flagged or ambiguous findings. If reviewers disagree, keep the item out until a revision clears the gate. |
| 3. Repair within a budget | Regenerate the failed item or dependent pack using the review findings and available course passages. Review each new revision against the same criteria. Start with one draft and at most two corrective regenerations per item, matching the existing material retry limit. Also cap elapsed time and calls per preparation run. Stop early when the same issue recurs with no new evidence or when required source material is absent. Retain passing checkpoints across retries. |
| 4. Publish the starter release | Replace the current six-question coverage rule with the verified starter minimum. Publish the validated graph, lessons, and starter bank atomically once their verification records match the content, sources, and gate version. During an update, serve the last verified release and preserve active session pins. If a first upload still fails, report the missing evidence or coverage and let the learner add sources or retry. A smaller verified unit is an option if it is clearly labelled, includes every prerequisite for its retained objectives, and passes the release checks for that scope. |

The acceptance cases cover a valid release that publishes automatically, a wrong answer key repaired and checked again, an unsupported claim that exhausts its budget, a failed update that leaves the last release usable, and a changed source that invalidates a saved verification record. Learner-facing progress should distinguish preparation, a ready release, and an actionable source gap. [Current release behavior](course-releases.md) · [Worker recovery](../learnloop/runtime/workflows.py)

### Shared learner memory and question requests

The Tutor reads a shared memory projection from existing assessment evidence and private activity notes in SQLite. The owner can download a `learner-memory.json` snapshot from `GET /api/courses/{id}/learner-memory`. Chat and planning receive summaries for their relevant objectives. The Assessor can use the same projection when its request workflow is added. [Learner memory](../learnloop/persistence/learner_memory.py) · [SQLite setup](sqlite-development.md)

- **Demonstrated strengths.** Derive them from validated assessment evidence at the target difficulty. Keep the difficulty, supporting assessment IDs, and review date so the Tutor can move on or schedule a check when review is due.
- **Gaps and uncertainty.** Record a specific skill or misconception, with difficulty, supporting activity or assessment IDs, source release, timestamp, and status. Use `suspected`, `corroborated`, and `resolved` to distinguish a hypothesis from repeated evidence and later recovery. Keep unassessed skills visible as unknown. [Evidence rules](../learnloop/core/domain.py)

1. **Record an observation.** The Tutor can submit a short observation about an apparent strength, confusion, or repeated hint use. The Assessor submits rubric-backed evidence of what the learner demonstrated or struggled with. The Expert can suggest an untested skill from the diagnostic summary. The runtime checks ownership and evidence references, appends each accepted observation once, and applies the evidence rules to update the summary. Tutor observations can guide practice. Demonstrating mastery or corroborating or resolving a gap requires independent assessment evidence. [Saved assessment evidence](../learnloop/agents/assessing/agent.py)
2. **Look for a saved question, then request one if needed.** The Tutor can request practice at a suitable difficulty and format. The Assessor can request a diagnostic question when a gap persists, evidence conflicts, or existing practice cannot distinguish between plausible explanations. First look for a suitable verified question that the learner has yet to answer. On a miss, record the objective, purpose, difficulty, format, pinned release, and any relevant gap and evidence IDs. Deduplicate equivalent pending requests and recheck the need before assigning the result.
3. **Generate, verify, and save for reuse.** Generate one question per request under the same automatic gate and bounded repair budget. Use the relevant course passages and, for a personalized request, the minimum diagnostic summary. Store verified general questions in a reusable course bank tied to the release. Store questions generated from learner evidence privately for that learner. Both banks sit alongside the immutable release, so saving a new question requires no course republication. Keep keys and rubrics private.
4. **Assign and reassess.** The Tutor considers the verified follow-up alongside other eligible activities. It checks prerequisites and current evidence and can offer an existing verified activity while the follow-up is prepared or if generation fails. The next response gives the Assessor evidence to keep the gap open, corroborate it, or resolve it. The runtime validates and saves the update.

For example, a learner selects the correct answer on a quantization quiz but explains it using the wrong scale convention. The Assessor can record a suspected confusion and request a fill-in calculation that distinguishes the two conventions. The Expert verifies the calculation and accepted answers against the source. The Tutor assigns it when eligible, and the Assessor uses the next response to update the gap.

### Direct quiz prerequisite decision

Keep lessons available to browse. A direct quiz can assign a new question when every direct prerequisite is currently demonstrated at its target difficulty. The same rule applies when the Tutor chooses the topic. A prerequisite due for review requires reassessment. Hinted answers and success below the target difficulty do not unlock the quiz. [Evidence rules](../learnloop/core/domain.py)

1. **Explain the block.** Show the learner which prerequisites are missing, the required difficulty, and whether each needs practice or review. Offer **Practice [prerequisite]** for an eligible next step. If the immediate prerequisite is itself blocked, offer an eligible topic farther back in the same chain.
2. **Keep the learner in control.** Keep the original quiz as the destination. Once the learner meets its prerequisites, offer **Start [original quiz]**. A blocked launch preserves the current activity and learner record. A question already assigned in the current session can be completed under its existing evidence rules. Recheck readiness before assigning the next question.
3. **Enforce at the API and at assignment.** Check the session's pinned release and the latest validated learner evidence before creating or retargeting a run. For a blocked direct launch, return a structured `409` with prerequisite details and the suggested next step. Recheck before committing an assignment so a delayed run cannot bypass a prerequisite that became due for review.

Acceptance cases include a blocked direct launch from a fresh or active session, a blocked switch that preserves an unanswered question, a prerequisite chain with an eligible starting point, and a successful launch after the required evidence is recorded. Confirm that lower-difficulty or assisted success leaves the gate closed and that a prerequisite becoming due while a question is being prepared blocks the new assignment.

## Assessing Agent (Reviewer)

The Reviewer grades four-option questions against private keys and weighted rubrics, with optional written reasoning. It records timing, hint use, misconceptions, and contradictions. Runtime rules determine what can change in the learner record, including when to mark a concept demonstrated, due for review, or developing after confirmed weakness. [Assessment workflow](../learnloop/agents/assessing/agent.py) · [Evidence rules](../learnloop/core/domain.py)

The study still needs to measure whether the judgments are accurate. [Evaluation guide](evaluation-harness.md) · [Evaluation metrics](../learnloop/evaluation/metrics.py)

## Implementation order and acceptance

1. **Starter bank and gate.** Accept when a new course publishes from verified lessons and Basic starter questions with zero Intermediate or Advanced generation calls during setup. Add typed question, answer, and rubric contracts for all four formats, and verify that existing single-answer activities remain usable.
2. **Question requests and learner memory.** Connect both agents to the shared memory and durable Expert requests. Accept when strengths and gaps persist across sessions, Tutor observations can influence practice, and mastery updates require validated assessment evidence. Verify that a bank hit skips generation, a duplicate request creates one job, and a verified result can be graded. Personalized questions stay private, and a stale or failed request leaves normal practice available. Track setup tokens and tokens per new verified question so the team can measure the savings.
3. **Research integration.** Apply the automated gate to frozen research inputs and define independent scoring for any new held-out formats before comparing results. Keep generated diagnostic questions inside each learner's practice and outside the held-out exam bank. Record which runs use fixed pools and which use live follow-up generation, since the current harness freezes practice pools. [Evaluation guide](evaluation-harness.md)
